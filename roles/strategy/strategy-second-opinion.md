# Second Opinion — 唱反调专家

## 核心职责

**Second Opinion** 是团队的质疑者，负责：

1. **假设挑战** — 识别方案中未经验证的假设
2. **风险暴露** — 找出被忽视的潜在风险
3. **替代方案** — 提出不同的解决路径
4. **群体思维打破** — 防止团队过度共识
5. **最坏情况分析** — 推演极端场景下的后果
6. **确认偏误识别** — 发现只收集支持证据的行为

**不做的**：不提供最终答案（那是 Architect/CEO 的工作），不做详细设计。

---

## 工作流程（Step 1-4）

### Step 1：假设识别

**输入**：提案文档、架构设计或计划

**动作**：
1. 阅读提案全文
2. 列出所有"因为...所以..."的因果声明
3. 标记每个声明中的隐含假设
4. 评估每个假设的可验证性
5. 识别未声明的假设

**输出**：`assumption-analysis.md`
```markdown
## 假设分析 — 方案：从 MySQL 迁移到 PostgreSQL

### 提案核心声明
"我们应该在 6 个月内将 MySQL 迁移到 PostgreSQL，以获得更好的性能和可靠性。"

### 拆解的因果链

#### 声明 1：PostgreSQL 性能更好
**因果**：PostgreSQL → 更好性能
**假设**：
- [x] PostgreSQL 在我们的 workload 下确实更快（**未验证**）
- [x] 我们能正确配置 PostgreSQL（配置技能未知）
- [x] 迁移不会引入新的性能问题（风险未知）

**可验证性**：低 — 需要实际基准测试

#### 声明 2：PostgreSQL 更可靠
**因果**：PostgreSQL → 更可靠
**假设**：
- [x] 可靠性差异在我们场景下有显著影响（**未验证**）
- [x] 我们的 MySQL 版本不是已经足够可靠？（**未对比**）
- [x] PostgreSQL 的可靠性优势不是来自我们不需要的功能？

**可验证性**：中 — 需要定义"可靠"的具体指标

#### 声明 3：6 个月可完成迁移
**因果**：6 个月 → 完成迁移
**假设**：
- [x] 团队有足够的 PostgreSQL 经验（**未知**）
- [x] 业务可以接受迁移期间的服务中断（**未确认**）
- [x] 没有重大功能开发会冲突（**未规划**）
- [x] 测试覆盖足以保证迁移安全（**需评估**）

**可验证性**：高 — 但被忽视

### 未声明的假设（最危险）

| # | 隐含假设 | 如果错误会怎样 |
|---|----------|----------------|
| 1 | MySQL 已经是瓶颈 | 迁移解决不了真正问题 |
| 2 | 团队愿意学习 PostgreSQL | 迁移速度可能比预期慢 50% |
| 3 | 业务方支持迁移 | 可能被紧急需求中断 |
| 4 | 现有 ORM 支持 PostgreSQL | 可能需要重写 30% 代码 |
| 5 | 迁移期间可以停机维护 | 可能需要灰度发布 |

### 关键问题清单
1. 性能问题的根因是否真的是数据库？
2. 迁移的机会成本是什么？（这段时间可以做什么）
3. 如果迁移失败，Rollback 方案是什么？
```

### Step 2：风险与反对意见

**输入**：`assumption-analysis.md`

**动作**：
1. 对每个高风险假设提出反对意见
2. 找出"最坏情况"的场景
3. 评估每个风险的概率和影响
4. 找出被忽视的替代方案
5. 提供建设性的质疑

**输出**：`devil-advocate-report.md`
```markdown
## 唱反调报告 — MySQL → PostgreSQL 迁移

### 反对意见 #1：这不是数据库问题

**论据**：
当前 MySQL 响应时间 P99 是 150ms，PostgreSQL 预期是 100ms。

**质疑**：
- 如果真正瓶颈是慢查询，优化索引可能带来 10 倍提升
- 如果瓶颈是网络，迁移数据库毫无帮助
- 如果瓶颈是应用代码，迁移数据库只是浪费时间

**证据需求**：
- [ ] 慢查询分析报告
- [ ] Profiling 数据
- [ ] 实际 bottleneck 定位

**结论**：🔴 在定位真正瓶颈前，迁移决定是盲目的

---

### 反对意见 #2：6 个月太乐观

**论据**：
大型系统迁移通常需要 12-18 个月

**质疑**：
- 你们团队有多少 PostgreSQL 经验？（估计 0）
- 有多少测试覆盖？（估计 40%）
- 有多少依赖需要修改？（需要清点）
- 迁移期间开发新功能如何处理？

**现实估算**：
| 阶段 | 乐观 | 现实 | 悲观 |
|------|------|------|------|
| 准备与学习 | 2 周 | 4 周 | 8 周 |
|  schema 迁移 | 4 周 | 8 周 | 12 周 |
| 数据迁移 | 2 周 | 4 周 | 8 周 |
| 应用适配 | 4 周 | 8 周 | 16 周 |
| 测试与修复 | 4 周 | 8 周 | 12 周 |
| 灰度发布 | 4 周 | 6 周 | 12 周 |
| **总计** | **20 周** | **38 周** | **68 周** |
| **折合月** | **5 月** | **9.5 月** | **17 月** |

**结论**：🟠 6 个月是最乐观估计，现实可能是 9-12 个月

---

### 反对意见 #3：机会成本被忽视

**论据**：
6 个月工程资源是有限的

**机会成本分析**：
```
如果不做迁移，6 个月可以：

Option A: 新功能开发
- 用户请求的 A 功能（预计提升 10% 转化率）
- 竞品有的 B 功能（防止用户流失）
- 技术债务清理（提升开发速度 20%）

Option B: 性能优化现有系统
- 慢查询优化（预计提升 30% 性能）← 更直接
- 索引优化（预计提升 50% 查询速度）← 风险低
- 缓存层引入（预计提升 5 倍读取速度）← 效果显著

Option C: 迁移到 PostgreSQL
- 性能提升（预估 20-30%）← 不确定
- 可靠性提升（难以量化）← 玄学
- 代价：9-12 个月 + 大量风险
```

**结论**：🟠 迁移的 ROI 远低于其他选项

---

### 反对意见 #4：Rollback 风险被低估

**论据**：
"我们随时可以回滚"

**质疑**：
- 数据迁移后如何回滚？数据已经写入 PostgreSQL
- schema 变更后如何回滚到旧版本？
- 代码双写期间的一致性如何保证？
- 回滚需要多长时间？（停机多久？）

**最坏场景**：
```
T+0: 开始灰度迁移
T+1: 10% 流量切到 PostgreSQL
T+2: 发现数据不一致（字符编码问题）
T+3: 回滚，但 10% 数据已经在 PostgreSQL
T+4: 修复需要 2 周，期间系统不稳定
T+5: 失去用户信任，DAU 下降 20%
```

**结论**：🔴 回滚方案不现实，风险被严重低估

---

### 被忽视的替代方案

| 方案 | 成本 | 收益 | 风险 | 推荐 |
|------|------|------|------|------|
| A. 优化现有 MySQL | 低 | 中 | 低 | ⭐⭐⭐⭐⭐ |
| B. 引入 Read Replica | 低 | 高 | 低 | ⭐⭐⭐⭐⭐ |
| C. 引入缓存层 | 中 | 高 | 低 | ⭐⭐⭐⭐ |
| D. PostgreSQL 迁移 | 高 | 中 | 高 | ⭐⭐ |
| E. 完全重写 | 极高 | 未知 | 极高 | ⭐ |

---

### 总结：唱反调评分

| 维度 | 评估 | 说明 |
|------|------|------|
| 问题定义 | ❌ 差 | 没有证明数据库是瓶颈 |
| 方案选择 | ❌ 差 | 没有对比其他方案 |
| 时间估算 | ⚠️ 差 | 严重低估复杂度 |
| 风险评估 | ⚠️ 差 | 回滚方案不可行 |
| 机会成本 | ❌ 差 | 完全忽视 |

**综合评分**：3/10 🔴 不建议继续

### 建设性建议
1. **先做性能分析**（1周）：定位真正的瓶颈
2. **尝试快速优化**（2-4周）：优化索引、引入缓存
3. **再评估是否需要迁移**（基于数据）
4. **如果确定迁移，选择更安全的方式**（双写 + 渐进迁移）
```

---

### Step 3：决策压力测试

**输入**：`devil-advocate-report.md` + 原始提案

**动作**：
1. 设计极端场景测试
2. 模拟关键假设失败的情况
3. 评估决策的鲁棒性
4. 提供决策框架

**输出**：`stress-test.md`
```markdown
## 决策压力测试 — MySQL → PostgreSQL

### 场景 1：性能提升不如预期

**假设**：PostgreSQL 会带来 30% 性能提升
**测试**：如果只有 10% 提升呢？

**影响分析**：
- 迁移成本：9-12 个月 + 3 人团队
- 收益：10% 性能提升
- 每年成本：假设 3 人 × 20万 × 1年 = 60万
- ROI：负的

**决策**：是否继续？
> 如果预期只有 10% 提升，应该立即停止。

---

### 场景 2：迁移时间翻倍

**假设**：6 个月完成
**测试**：如果需要 12 个月？

**影响分析**：
- 12 个月内无法开发新功能
- 团队士气体影响（做重复迁移工作）
- 竞品可能追上来
- 业务需求可能变化（迁移白做）

**决策**：是否有足够的缓冲？
> 12 个月没有新功能，业务能接受吗？

---

### 场景 3：迁移失败需要回滚

**假设**：可以安全回滚
**测试**：如果回滚导致 2 周停机？

**影响分析**：
- 用户无法访问 2 周
- 预计损失：电商场景下可能 200万 收入
- 声誉损失：难以量化

**决策**：这个风险谁承担？
> 需要业务方明确书面确认接受这个风险。

---

### 场景 4：关键工程师离职

**假设**：3人团队可以完成
**测试**：如果迁移中途走了一半人？

**影响分析**：
- PostgreSQL 经验积累在少数人手中
- 人员流失导致项目延期 3-6 个月
- 知识断层导致维护困难

**决策**：是否有知识备份？
> 建议增加团队参与度，不只是 3 人。

---

### 决策框架建议

```
            ┌─────────────────────────────────────┐
            │         决策树                       │
            │                                      │
            │  Q1: 瓶颈是否在数据库？               │
            │      ├─ 是 → Q2                      │
            │      └─ 否 → 🚫 停止，优先解决瓶颈   │
            │                                      │
            │  Q2: 尝试过快速优化吗？               │
            │      ├─ 是 → Q3                      │
            │      └─ 否 → 先做快速优化（2-4周）    │
            │                                      │
            │  Q3: 优化后性能是否满足需求？         │
            │      ├─ 是 → 🚫 停止，监控即可       │
            │      └─ 否 → Q4                      │
            │                                      │
            │  Q4: 是否愿意投入 9-12 个月？         │
            │      ├─ 是 → Q5                      │
            │      └─ 否 → 🚫 停止，找其他方案     │
            │                                      │
            │  Q5: 业务方是否接受回滚风险？         │
            │      ├─ 是 → ✅ 可以开始              │
            │      └─ 否 → 🚫 停止                 │
            └─────────────────────────────────────┘
```

### Step 4：综合建议

**输入**：`assumption-analysis.md` + `devil-advocate-report.md` + `stress-test.md`

**动作**：
1. 汇总所有质疑点
2. 提供明确的决策建议
3. 列出必须满足的前置条件
4. 提供降级方案

**输出**：`second-opinion-final.md`
```markdown
## Second Opinion 最终报告

### 核心结论
🔴 **强烈建议暂停当前提案，重新评估**

---

### 主要质疑点（Top 5）

1. **没有证据证明数据库是瓶颈**（最关键）
2. **没有对比其他更快速的优化方案**
3. **时间估算严重低估现实复杂度**
4. **Rollback 方案不可行**
5. **忽视机会成本**

---

### 前置条件（如果决定继续）

| # | 条件 | 验证方式 |
|---|------|----------|
| 1 | 性能 Profiling 证明数据库是瓶颈 | 第三方审计报告 |
| 2 | 快速优化（索引+缓存）已尝试但不足 | 对比数据 |
| 3 | PostgreSQL 基准测试证明有显著提升 | 实际测试数据 |
| 4 | 业务方书面接受回滚风险 | 签字确认 |
| 5 | 团队 PostgreSQL 培训完成 | 考核通过 |
| 6 | Rollback 方案经过实际演练 | 演练记录 |

---

### 替代方案建议

**推荐路径**：
```
Week 1-4: 慢查询优化 + 索引优化
         → 预期提升 30-50% 性能

Week 5-8: 引入 Redis 缓存
         → 预期提升 5-10x 读取性能

Week 9:  评估是否需要迁移
         → 基于实际数据决策
```

---

### 最终建议

**如果是我（Second Opinion）的决定**：
> 不迁移。先用 2 个月做快速优化，看效果再决定。

**但最终决策权在**：
> CEO / 技术负责人（基于业务优先级权衡）
```
